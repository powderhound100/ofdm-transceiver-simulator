2. LDPC Encoder — Deep Dive

The Parity-Check Matrix H

The foundation of any LDPC code is its parity-check matrix H, a sparse binary matrix of dimensions M×N where M = N - K. For our 802.11n rate-1/2 code:

ParameterValueMeaning
N648Codeword length (bits)
K324Information bits
M324Parity-check equations
Z27Lifting factor (circulant block size)
Base matrix12×24Each entry expands to a 27×27 circulant
Rank(H)3204 dependent rows (normal for 802.11n)
Total edges2,376Non-zero entries in H

QC-LDPC Structure

The matrix H is not random — it has Quasi-Cyclic (QC) structure. The 12×24 base matrix contains entries in {-1, 0, 1, ..., 26}. Each entry s expands to a 27×27 circulant permutation matrix (the identity matrix cyclically shifted right by s positions). Entry -1 expands to the all-zero matrix.

This structure is what makes the code both powerful and practical:

  • Encoding: The near-staircase parity submatrix enables O(N) encoding via back-substitution
  • Decoding: The QC structure means Z=27 check nodes in the same row-block have identical connectivity patterns (just shifted) — perfect for SIMD parallelism in Rust and barrel-shifter routing in FPGA
  • Storage: Only the 12×24 base matrix needs to be stored (288 values), not the full 324×648 H matrix

Encoding Algorithm

Given information bits i (length K=324), we need parity bits p (length M=324) such that H·[i | p]T = 0 (mod 2).

Method: Pre-computed GF(2) Inverse
Partition H = [Hinfo | Hparity]. The syndrome is s = Hinfo·i (mod 2). The parity bits are p = Hparity-1·s (mod 2). We pre-compute Hparity-1 once at initialization using Gaussian elimination over GF(2). Per-frame cost drops from O(M3) to O(M·K).

Test 2: Cross-check Gaussian elimination (100 trials)...
  PASS: Both methods produce identical codewords
Test 3: All-zero info bits...
  PASS: All-zero codeword

3. LDPC Decoder — Normalized Min-Sum

Why Min-Sum Instead of Belief Propagation?

Belief Propagation (BP)

CNU computes: product of tanh(v2c/2)

Needs lookup tables or CORDIC

Best performance (~0 dB from Shannon)

Complex in hardware

Normalized Min-Sum (NMS)

CNU computes: min of |v2c| × XOR of signs

Just comparators + XOR gates

~0.2 dB from BP (with α=0.75)

10x simpler in hardware

Our Choice

NMS with α = 0.75

0.75 = 1 - 1/4 = x - (x >>> 2)

Zero DSP slices needed

Standard in all commercial decoders

The Algorithm in Detail

The decoder operates on the Tanner graph — a bipartite graph with N=648 variable nodes (one per bit) and M=324 check nodes (one per parity equation). Messages flow along the 2,376 edges connecting them.

Initialization

c2v[c][j] = 0.0  for all check nodes c, all edges j
# No prior information from check nodes

Variable Node Update (VNU)

for each variable node v:
    posterior[v] = channel_llr[v] + sum(c2v[c -> v] for all check nodes c connected to v)
    for each connected check node c:
        v2c[v -> c] = posterior[v] - c2v[c -> v]   # Extrinsic principle!

The extrinsic principle is critical: the message from v to c must NOT include information that c already sent to v. Subtracting c2v[c→v] ensures each message carries only independent evidence. Without this, the decoder would "echo" information and fail to converge.

Syndrome Check (Early Termination)

hard_bits[v] = 1 if posterior[v] < 0 else 0
syndrome[c] = XOR of hard_bits[v] for all v connected to c
if all syndrome[c] == 0:  # Valid codeword found!
    return hard_bits       # Stop early — saves power and latency

Check Node Update (CNU) — The Min-Sum Core

for each check node c:
    # Gather incoming messages
    signs[j] = sign(v2c[j])          # +1 or -1
    magnitudes[j] = |v2c[j]|

    # XOR all signs (parity of negative messages)
    sign_product = product(signs[j])

    # Find two smallest magnitudes
    min1, min2, argmin1 = find_two_smallest(magnitudes)

    # Send outgoing messages
    for each edge j:
        ext_sign = sign_product * signs[j]   # Flip sign for extrinsic
        mag = min2 if j == argmin1 else min1  # The OTHER minimum
        c2v[c][j] = alpha * ext_sign * mag    # alpha = 0.75 normalization
Why does min-sum work? The exact BP update computes 2·atanh(∏ tanh(v2c/2)), which is dominated by the smallest magnitude input. The min-sum approximation replaces this with just the minimum magnitude, scaled by α=0.75 to compensate for the overestimation. The "min2" architecture means we only store two values per check node instead of all edge messages — critical for FPGA BRAM efficiency.

4. Channel Modeling — Why It Matters

The channel model determines what the receiver "sees" after the signal travels from transmitter to antenna. Getting this right is essential — a decoder tested only on AWGN will fail spectacularly on real-world multipath signals.

The Three Channel Models

1. Flat (AWGN Only)

Impulse response: h = [1.0] (single tap, unity gain)

What it models: Line-of-sight reception with no reflections. The signal arrives perfectly, just with additive white Gaussian noise.

When it's realistic: Rural areas, rooftop antennas pointed at nearby transmitters. Also the theoretical baseline for comparing code performance.

Effect on OFDM: All subcarriers experience identical SNR. Channel estimation is trivial. This is the "easy" case.

H(f) = |1.0| = 0 dB for all frequencies
Every subcarrier sees the same channel.

2. Two-Tap

Impulse response: h = [1.0, 0, 0, 0, 0, 0.707] (main path + reflection at -3 dB, 5 samples delayed)

What it models: A single strong reflection — e.g., a signal bouncing off a nearby building. The delayed copy creates frequency-selective fading with periodic nulls.

When it's realistic: Suburban areas with one dominant reflector (building, hill).

Effect on OFDM: The frequency response has a sinusoidal pattern of peaks and nulls. Subcarriers near nulls experience very low SNR, while others are boosted. The LDPC code must correct errors concentrated on the faded subcarriers.

H(f) = 1 + 0.707 * exp(-j*2*pi*f*5/Fs)
|H(f)| oscillates between +4 dB and -10 dB across the band.

3. TU-6 (Typical Urban, 6 Taps)

Impulse response:

TapDelay (samples)Power (dB)Physical meaning
10-3.0Direct path (partially obstructed)
210.0Ground reflection (strongest path)
33-2.0Nearby building reflection
45-6.0Distant building reflection
58-8.0Far scatter
612-10.0Diffuse multipath tail

What it models: The standard ITU Typical Urban channel. Multiple reflections from buildings, ground, and distant scatterers create a complex frequency response with deep, narrow nulls.

When it's realistic: Urban DTV reception — the most common real-world scenario. The channel varies unpredictably across frequency, and some subcarriers may be completely wiped out.

Effect on OFDM: Severe frequency-selective fading. Pilot-based channel estimation must accurately track the channel across all subcarriers, and the LDPC code must handle burst errors from faded spectral regions.

Why Multipath Creates the Need for OFDM

In a single-carrier system (like ATSC 1.0's 8VSB), multipath causes inter-symbol interference (ISI) — delayed copies of previous symbols overlap with the current symbol. Fixing this requires complex adaptive equalizers.

OFDM solves this elegantly: by splitting the wideband channel into many narrow subcarriers, each subcarrier sees an approximately flat channel. The cyclic prefix (CP) absorbs the multipath delay spread, preventing ISI between OFDM symbols. The remaining effect is per-subcarrier amplitude/phase distortion, which is corrected by simple one-tap equalization: X_eq = Y / H_est.

Critical insight: The cyclic prefix must be longer than the maximum channel delay spread. Our CP = 16 samples, and the TU-6 model has maximum delay = 12 samples. Since 16 > 12, the CP fully absorbs the multipath, and we get ISI-free reception. If CP were only 8 samples, the TU-6 channel would cause ISI, and performance would degrade dramatically.

5. Channel Estimation & Equalization

After OFDM demodulation (FFT), each received subcarrier is Y[k] = H[k]·X[k] + W[k], where H[k] is the unknown channel at frequency k and W[k] is noise. To recover X[k], we need to estimate H[k].

Pilot-Based Least-Squares (LS) Estimation

We transmit known pilot symbols (P[k] = 1+0j) on specific subcarriers. At the receiver:

# At pilot subcarrier positions (every 12th subcarrier):
H_pilot[k] = Y_pilot[k] / P[k]    # Since P[k] = 1, this is just Y_pilot[k]

# Interpolate to all data subcarriers:
H_est[k] = interpolate(pilot_positions, H_pilot, all_positions)

# Zero-forcing equalization:
X_eq[k] = Y[k] / H_est[k]

Pilot Configuration

ParameterValueWhy
FFT size64Demonstration size; real ATSC 3.0 uses 8K/16K/32K
Data subcarriers48Carries QAM symbols
Pilot subcarriers4Known reference values for channel estimation
Pilot spacingEvery 12thMust satisfy Nyquist criterion for channel bandwidth
Pilot value1.0 + 0jBPSK pilot; makes LS estimation trivial (divide by 1)

Why LS Estimation Works (and When It Doesn't)

Flat channel: H[k] is constant across all subcarriers. Even with only 4 pilots, the interpolation is perfect. Channel estimation adds negligible error.

Two-tap channel: H[k] has a sinusoidal variation. Linear interpolation between 4 pilots captures the trend but may miss exact null positions. Performance degrades by ~1-2 dB compared to perfect channel knowledge.

TU-6 channel: H[k] has rapid, deep variations. Four pilots spaced 12 subcarriers apart cannot capture narrow nulls (which may be only 2-3 subcarriers wide). This causes estimation error at the faded subcarriers, leading to noise enhancement during equalization (dividing by a small estimated H amplifies noise). This is why TU-6 performance requires significantly higher SNR.

Future improvement: ATSC 3.0 uses many more pilots (scattered + continual) and MMSE estimation with noise regularization. Our simplified LS estimator demonstrates the concept; a production receiver would use H_mmse = H_ls * SNR / (SNR + 1) to avoid noise amplification at faded subcarriers.

Zero-Forcing Equalization

After estimating H[k], we equalize: X_eq[k] = Y[k] / H_est[k]. This is "zero-forcing" because it forces inter-carrier interference to zero. The cost: noise enhancement at frequencies where |H_est[k]| is small. A better approach (MMSE equalization) would be: X_eq = H* / (|H|^2 + 1/SNR) * Y, trading some residual interference for reduced noise amplification.

What the Test Data Looks Like

f32 LLR Values (channel input to decoder)

At +2.0 dB SNR, a typical LLR vector has:

  • Mean |LLR| ≈ 3.5 (moderate confidence)
  • Most LLRs have correct sign (matching transmitted bit)
  • A few LLRs have wrong sign (noise flipped them) — these are the errors the LDPC code must correct

6-bit Quantized LLR (FPGA input)

The f32 values are quantized to 6-bit signed integers [-31, +31] using 2's complement. This is the FPGA's native datapath width. The quantization adds < 0.1 dB loss vs floating-point — well characterized in the literature.

Per-Iteration Messages

For the clean (+2 dB) case, we store 12 iteration snapshots. Each contains:

  • c2v_iterNN.hex: 324 lines, each line has space-separated hex values for each edge out of that check node
  • v2c_iterNN.hex: 648 lines, each line has hex values for edges out of that variable node
  • posterior_iterNN.hex: 648 hex values (6-bit quantized posterior LLR)
  • syndrome_iterNN.txt: "PASS" or "FAIL"

Why This Test Data Mimics Real-World Scenarios

Noiseless (∞ dB) — Manufacturing Test

In real systems, this is the equivalent of a "loopback test" where the transmitter output is connected directly to the receiver input. It validates that the digital signal processing chain works without any analog impairments. Every hardware LDPC decoder must pass this test before deployment.

Clean (+2 dB) — Strong Local Signal

This represents receiving a TV station within 10-20 miles with a decent antenna. The signal has some noise but the LDPC code handles it easily. In real ATSC 3.0, this corresponds to the "core service area" where broadcast reliability is designed to be >99%.

Waterfall (-0.5 dB) — Fringe Reception

This is the boundary of reliable reception — the "cliff edge" where LDPC either saves you or doesn't. In real DTV, this is 40-60 miles from the transmitter. The BER is highly variable frame-to-frame, and a real receiver would switch to a more robust code rate.

High Noise (-2 dB) — Beyond Coverage

Below the waterfall. No amount of LDPC decoding can recover the data at this code rate. In real systems, this triggers an "outage" condition. The test validates that the decoder doesn't crash, hang, or produce garbage — it should exit gracefully after max_iter.

The f32 Precision Requirement

A critical discovery during testing: Python uses f64 (double precision) internally, but test vectors are stored as f32 (single precision). When Rust reads the f32 files and decodes, the accumulated rounding difference over 50 iterations can flip marginal bits differently than Python's f64 decode of the original f64 LLR.

Solution: Python now quantizes LLR through f32 before decoding: llr_f32 = llr.astype(np.float32).astype(np.float64). This ensures both implementations decode from bit-identical f32 input, and produce bit-identical output. This matches the real-world scenario where ADC/DAC precision limits LLR to fixed-point anyway.

What the BER Data Teaches Us

1. LDPC coding gain on flat channel: ~7 dB

At QPSK: uncoded BER=0 requires ~14 dB SNR. With LDPC, BER=0 at 7 dB. That's 7 dB of coding gain — the LDPC code is doing massive heavy lifting, correcting hundreds of bit errors per frame.

2. Modulation order shifts the waterfall predictably

QPSK→7 dB, 16QAM→10 dB, 64QAM→15 dB. The ~3 dB gap per doubling follows the theoretical minimum distance scaling of QAM constellations. A production system uses adaptive modulation: QPSK for weak signals, 64QAM for strong, maximizing throughput at every SNR.

3. Channel estimation is the bottleneck, not the LDPC code

The two-tap and TU-6 results prove the LDPC decoder is not the weak link. The decoder works perfectly when given good LLRs (flat channel). The problem is upstream: the equalized symbols have wrong phase/amplitude due to poor channel estimation, producing LLRs with wrong signs that no decoder can fix.

4. Iteration count tracks SNR precisely

QPSK flat: 50 iterations (not converging) at 3 dB, 7 iterations at 7 dB, 1 iteration at 12+ dB. This means a real-time decoder can use early termination to save 80%+ of computation on strong signals — crucial for power efficiency in mobile receivers.

10. Technical Tradeoffs & Design Decisions

Decision 1: Normalized Min-Sum vs Belief Propagation

Chose: NMS with α=0.75

Gave up: ~0.2 dB coding gain

Gained: 10x simpler hardware (no LUTs for tanh/atanh), zero DSP slices for alpha (bit shift), identical algorithm across all 3 implementations, well-understood fixed-point behavior

Verdict: Universal choice in commercial LDPC decoders. The 0.2 dB is recovered by adding ~0.5 extra iterations on average.

Decision 2: Flooding vs Layered Decoding

Chose: Flooding for Python/Rust (simplicity), layered planned for FPGA (throughput)

Tradeoff: Layered decoding converges in ~half the iterations (immediate belief updates propagate faster), doubling effective throughput. But it requires read-modify-write of variable beliefs (more complex memory access pattern) and is harder to verify against a flooding reference.

Plan: Validate the flooding FPGA first (bit-exact with Python). Then add layered mode and verify it converges to the same codeword (possibly in fewer iterations).

Decision 3: f64 Internal Precision in Rust

Chose: f64 internal arithmetic with f32 input

Gave up: ~2x slower than pure f32 (wider registers, less SIMD parallelism)

Gained: Bit-exact match with Python for all 4 test vectors, including non-converging cases where 50 iterations of accumulated rounding would diverge

The f32 SIMD path exists for high-throughput mode where bit-exact Python match isn't required (e.g., real-time BER sweeps).

Decision 4: 802.11n Mock Code vs Full ATSC 3.0

Chose: IEEE 802.11n rate-1/2 N=648 Z=27 as the development code

Why not ATSC 3.0 directly? Full ATSC 3.0 codes are N=64,800, Z=360. GF(2) encoder inverse is infeasible (M=56,160). Python decoder takes ~30 seconds per frame. FPGA barrel shifter needs 360-wide muxes. Everything is 100x harder to debug.

Path to ATSC 3.0: The code is parameterized. Changing the base matrix and Z scales everything. The 802.11n code validates the algorithm; the ATSC 3.0 code validates the parameters.

Decision 5: Min2 Architecture for FPGA

Chose: Store (min1, min2, argmin1, sign_product, signs) per check node instead of all edge messages

Saved: ~60% BRAM. Full edge storage for N=648: 6 bits × 2,376 edges ≈ 1.8 KB. For N=64,800: 6 bits × ~200K edges ≈ 150 KB (exceeds Artix-7 BRAM).

Min2 cost: ~40 bits per check node × 324 check nodes ≈ 1.6 KB. Scales to full ATSC 3.0 at ~5 KB.

Tradeoff: The CNU must process column blocks sequentially (accumulating min/sign) rather than accessing all edges in parallel. This adds latency but is the standard approach in all area-constrained LDPC decoder ASICs.

Decision 6: LS vs MMSE Channel Estimation

Chose: Least-Squares (LS) with linear interpolation

Simplicity: H_est = Y_pilot / P_pilot. One complex division per pilot. No matrix inversion, no noise variance estimation required.

Cost: ~3-5 dB worse than MMSE on multipath channels (noise amplification at faded subcarriers)

Why acceptable: This is a simulation framework for validating the LDPC decoder, not a production ATSC 3.0 receiver. The channel estimation quality shows clearly in the dashboard (compare True vs Estimated H(f) plot). Upgrading to MMSE is a straightforward improvement once the decoder is proven.

12. References & Open-Source Validation

No open-source ATSC 3.0 LDPC decoder (software or RTL) currently exists — this project would be the first. The following open-source projects are used for validation and architectural reference.

Priority 1: gr-atsc3 — ATSC 3.0 Base Matrices

Repo: github.com/drmpeg/gr-atsc3  |  Author: Ron Economos (drmpeg)  |  License: GPL-3.0

Verified against the official ATSC 3.0 V&V test suite. Contains the complete A/322 LDPC parity accumulator tables for all 24 codes (12 rates × 2 frame lengths) in lib/ldpc_bb_impl.cc, plus code parameters in lib/params.cc.

How we use it: Extract tables into our ldpc_code.py format; validate our encoder output; use V&V test flowgraphs as additional verification beyond BER tests.

Priority 2: AFF3CT — Algorithm Validation & BER Reference

Repo: github.com/aff3ct/aff3ct  |  License: MIT

High-performance C++ LDPC encoder/decoder with SIMD (SSE/AVX/NEON). Supports Min-Sum variants (MIN, MINL, MINS/min-star) and Belief Propagation. DVB-S2 codes built-in; custom codes via AList/QC format.

How we use it: Convert our ATSC 3.0 H matrices to AList format; run independent BER curves at the same SNR points; cross-validate our Python/Rust BER against AFF3CT; compare min-sum normalization performance (our α=0.75 vs AFF3CT variants).

Priority 3: FEC-Archive-Verilog — FPGA RTL Architecture Reference

Repo: github.com/Lcrypto/FEC-Archive-Verilog

WiMAX (802.16e) QC-LDPC Normalized Min-Sum decoder in Verilog, rates 1/2 to 5/6 at length 2304. Synthesized on Cyclone IV: 210 MHz, 11,872 LCs, 37 M9K BRAMs. Contains CNU, VNU, and barrel shifter RTL modules.

How we use it: Study RTL patterns for CNU/VNU pipeline, barrel shifter, BRAM partitioning. Compare resource estimates. Adapt QC-LDPC routing structure for Z=360 (they use Z=96). Not directly reusable (different code parameters), but same decoder algorithm.

Priority 4: dvb_fpga — LDPC Encoder RTL & Test Infrastructure

Repo: github.com/OpenResearchInstitute/dvb_fpga  |  License: CERN-OHL-W v2

DVB-S2 LDPC encoder in VHDL with AXI-Stream interfaces (~1,017 LUTs + 558 FFs). Table ROM organization (ldpc_tables_pkg.vhd) uses the same format as ATSC A/322. The DVB-S2 Type B (IRA) encoding is identical to ATSC 3.0 Type B.

How we use it: Adapt table ROM organization for ATSC 3.0 parameters; follow AXI-Stream interface patterns for our FPGA I/O. Their decoder is missing — they want exactly what we're building.
